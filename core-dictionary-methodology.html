BIM-CDE Core Dictionary Methodology

建筑全生命周期工程对象字典与数据联动方法论

以工程实际业务为基础，建立独立于国标、IFC、Revit Category 的 Core Dictionary，通过映射层连接设计、招标、施工、造价、运维和 AI 自动化，让平台可以精准理解“对象是什么、属于哪里、需要哪些信息、能与什么系统联动”。

01｜为什么需要工程对象字典

传统 BIM 分类通常依赖软件类别、企业编码或专业经验。它们可以支持建模和出图，但很难支撑跨软件、跨阶段、跨参建方的数据联动。

设计招标施工造价运维AI

软件类别不等于工程语义

Revit Category、IFC Entity、国标编码都各有用途，但不能直接作为平台内部唯一语义。比如“墙”在结构、建筑、防火、围护、装修中含义不同，不能只靠一个 Category 判断。

项目阶段需要信息深度

方案阶段只需要对象占位和大致尺寸；施工图、招标、施工、结算、运维阶段需要逐步补充材料、做法、工程量、合同责任、设备状态等信息。

自动化需要可计算链路

平台要自动生成明细表、查漏缺项、判断合同责任、执行 AI 查询，就必须知道对象的 domain、discipline、functionality、type、Pset 和映射关系。

02｜核心方法：原创语义内核 + 多层映射隔离

Core Dictionary 不复制任何单一标准，而是先定义平台自己的工程语义，再通过映射层对接国标、地标、IFC、Revit、其他 BIM 软件和项目自定义属性。

Core Dictionary -> semanticPath / dictionaryId -> Domain + Discipline + Functionality + ObjectType -> Pset / Property / LOIN -> External Mapping -> GB/T / 地标 / IFC / Revit Category / 软件属性 / 企业编码 -> Project Layer -> SubType / Instance / SystemInstance / WorkPackage / ContractBOQItem
Domain对象处于哪一种业务维度：Project、System、Component、Part、Assembly、DrawingObject、ScheduleTask、CostObject 等。
Discipline对象主要由哪个专业负责：Architecture、Structure、Facade、HVAC、Plumbing、Electrical、Interior 等。
Functionality对象承担什么功能：LoadBearing、FireProtection、Drainage、Conveying、AirConditioning、Acoustic、Thermal 等。
ObjectType程序字典定义到 Type；SubType 由项目定义，Instance 由设计师或系统创建。

03｜1D-5D 对象体系

Component / Part / Assembly 只适用于 3D 建模对象。项目、图纸、进度、造价各自有自己的层级逻辑，不能把 3D 的嵌套规则套到所有对象上。

维度对象域典型 ObjectType核心作用
1D 信息对象Project / System / Organization / Rule / StandardProject、Stakeholder、ResponsibilityAssignment、CurtainWallSystem、AirConditioningSystem承载项目、组织、系统、规则和责任信息，是跨模块联动的主索引。
2D 图纸对象DrawingObject / DeliverableDrawingSheet、DrawingView、Dimension、HatchPattern、LegendSymbol支撑出图、图纸校审、图模一致性、交付物管理。
3D 模型对象Space / Component / Part / AssemblyWall、Window、Stair、StairBeam、CurtainWallMullion、Rebar、Concrete支撑建模、可视化、出量、碰撞、深化、运维定位。
4D 进度对象ScheduleTask / WorkPackage / ResourceSchedulePlan、WBS、Activity、ConstructionWorkPackage连接模型对象与施工组织、工序、资源、进度计划。
5D 造价对象CostObject / BOQ / QTOBIMQuantity、TenderBOQItem、ContractBOQItem、CompositeUnitPrice、PaymentValuation连接 BIM 实物量、清单计价、合同价款、变更和结算。
3D 中 Component 是建筑设计出图的最小业务单元；Part 是 Component 内可独立建模、计算、出量或深化的分部；Assembly 是 Part 或 Component 内部更细的材料、配件、零件或装配组成。

04｜Pset 与 LOIN：让每个对象“刚好够用”

每一种 Domain、Discipline、Functionality 都可以有自己的 Pset。ObjectType 的有效 Pset 是前面三层的合集，再加上 Type 自有 Pset。Pset 只定义字段结构、边界和信息要求，具体值属于项目 SubType 或 Instance。

Domain Pset对象所属业务域的通用字段，例如 Component 身份、SystemRef。
Discipline Pset专业字段，例如结构计算、机电系统、幕墙分格。
Functionality Pset功能字段，例如承重、消防、防水、声学、热工。
Type Pset具体类型字段，例如梁几何、窗扇、风管、合同清单项。
SubType Value项目定义的类型值，例如 1000x1000 平开窗、C30 梁。
Instance Value模型或业务系统中每个实例的编号、位置和实测参数。

LOD 是显示与加载策略

LOD 用于平台性能优化。城市级视图加载项目外观和道路设施，项目级视图加载 Component，双击进入 Part，再进入 Assembly，实现层级浏览。

LOIN 是信息需求深度

LOIN 决定不同阶段需要哪些属性。Pset 应覆盖该对象涉及阶段的必要信息，不让设计师填无关空值，也不让关键字段缺失。

05｜标准与软件映射：隔离层而不是依赖层

Core Dictionary 必须具备原创性，同时可与外部标准双向映射。这样既能保持平台语义稳定，也能兼容设计院、施工单位、造价咨询、运维单位各自的软件和标准体系。

映射对象映射方式用途边界
国标 / 地标通过 ExternalMapping 记录标准编码、名称、适用条件、证据等级。满足审查、交付、归档、政府平台或地方标准要求。国标不反向决定 Core Type，只作为对照与校验依据。
IFC / openBIM映射 IFC Entity、PredefinedType、PropertySet、IDS 约束。支持跨软件交换、openBIM 交付、IFC 校验和长期归档。IFC Entity 粒度不一定等于工程业务粒度，需要条件映射。
Revit / 其他 BIM 软件映射 Category、Family、Type Name、Shared Parameter、内置参数。支持插件自动识别、过滤、批量赋参、明细表生成。软件字段只作为输入证据，不能成为平台唯一分类。
企业编码 / 项目编码通过 displayCode、legacyCode、project subtype、instanceId 管理。兼容历史表格、合同清单、项目命名习惯。项目命名空间与 Core Dictionary 命名空间分离。

06｜AI 与自动化：从“点选过滤”变成“语义查询”

字典链路的最终目标不是把分类做漂亮，而是让用户少点选、少自定义、少研究过滤器。平台应该能预判用户意图，并把正确对象、属性、清单和责任边界自动查出来。

语义查询

用户说“我要所有消防相关构件”，系统过滤 functionality=FireProtection，跨 Architecture、Plumbing、Electrical、HVAC、Interior 返回结果。

自动明细表

系统根据 ObjectType 的有效 Pset 自动生成字段，不需要用户手动研究 Revit 过滤器、共享参数和清单字段。

查漏缺项

招标模型可比对 BIMQuantity、TenderBOQItem、ContractBOQItem、WorkPackage，识别漏项、差值和责任边界。

User Intent: “查所有承重对象” -> functionality = LoadBearing -> ObjectType: Beam / StructuralWall / CurtainWallMullion / StairBeam / StairColumn / StairFlight -> Effective Pset: Identity + SystemRef + LoadBearingCalc + TypeGeometry -> Output: 明细表 / 校验项 / QTO / AI 解释 / Revit 过滤器

07｜工程实现路径：Excel 审阅主表 + JSON 执行包 + Core API

业务侧用 Excel 审阅，程序侧用 JSON 执行，平台侧通过 Core API 消费。三者之间由导出脚本和 Validator 保证一致。

Excel Review Workbook

维护 DomainIndex、DisciplineIndex、FunctionalityIndex、ObjectTypes、PsetDefinitions、Decisions 等业务审阅内容。

Generated JSON Package

导出 code-registry.json、type-definitions.json、pset-definitions.json 等可执行数据。

Core API & Simulator

提供正向查询、反向索引、Pset 合集、Validator 和链路模拟，支撑后续插件、CDE 和 AI 应用。

核心字段作用示例
dictionaryId短机器主键，用于程序、数据库、API、关系引用。ot_jz6v6ocfvyto4cbv
semanticPath结构化语义路径数组，避免分隔符歧义。["core","type","component","structure","loadbearing","beam","v1"]
semanticCode由 semanticPath 派生的可读路径。core/type/component/structure/loadbearing/beam/v1
displayCode面向 Excel、报告、文档、人工沟通的显示编码。CORE-TYPE-CMP-STRUCT-LOADBEARING-BEAM-v1

08｜对 BIM-CDE 平台的价值

精准过滤按功能、专业、对象域、类型组合过滤，减少用户手工筛选。
自动赋参通过 Pset 合集知道该对象需要哪些字段，避免多填和漏填。
跨阶段联动设计对象可关联招标清单、合同清单、施工包、进度任务和运维资产。
AI 可理解AI 可以沿 dictionaryId、semanticPath、Pset、Mapping 进行语义推理。

09｜治理机制：高内聚、低耦合、可演进

字典是 BIM-CDE 的语义内核，必须与业务模块解耦。分类、映射、权限、数据敏感度、系统引用、项目实例都应有清晰边界。

权限与敏感属性

Pset Property 可声明 dataSensitivity、permissionDomain、defaultReadPolicy，后续由管理员配置模块访问、读取和操作权限。

坐标与平台尺度

自研 BIM + GIS + CIM 平台应采用局部平面坐标与大地坐标映射方案，支持项目坐标、国家大地 2000、地方坐标和父子对象局部坐标。
